Chapter 1

메시지는 큐로 바로 가지 않는다

RabbitMQ는 서비스 사이에 메시지를 맡아두는 브로커다. Producer는 메시지를 발행하고, Exchange는 규칙에 맞는 Queue를 고르며, Consumer는 Queue에서 메시지를 가져가 처리한다.

핵심 메모

주문 시스템에서 사용자는 주문 접수만 빠르게 확인하면 된다. 오래 걸리는 결제, 재고, 알림 처리는 뒤에서 비동기로 처리하면 사용자 경험과 시스템 안정성이 같이 좋아진다.

  • AMQP는 서로 다른 언어와 플랫폼이 같은 방식으로 메시지를 교환하게 해주는 표준 프로토콜이다.
  • Exchange는 메시지를 어느 Queue로 보낼지 결정하는 라우터다.
  • Queue는 Consumer가 가져가기 전까지 메시지를 저장한다.
  • Binding은 Exchange와 Queue 사이의 라우팅 규칙이다.

    Chapter 2

    Work Queue는 일을 나눠서 처리한다

    여러 Consumer가 같은 Queue를 바라보면 메시지는 한 Consumer에게만 전달된다. ready는 아직 안 간 메시지, unacked는 전달됐지만 ACK가 돌아오지 않은 메시지다.

    핵심 메모

    기본 분배는 Round-Robin이다. 작업 시간이 비슷하면 단순하고 좋지만, 긴 작업과 짧은 작업이 섞이면 한 Consumer에게 일이 몰린 것처럼 보일 수 있다.

    • AUTO ACK는 리스너가 정상 종료되면 자동으로 ACK를 보낸다.
    • MANUAL ACK는 처리 완료 시점에 직접 ACK를 보낸다.
    • prefetchCount를 제한하면 먼저 끝난 Consumer가 다음 작업을 받기 쉬워진다.
    • purge는 보통 ready 메시지를 비우며, unacked는 연결 상태에 따라 다르게 보인다.

      Chapter 3

      Exchange가 Queue를 고르고, 실패는 DLQ로 흐른다

      Producer는 Queue 이름을 몰라도 된다. Exchange 이름과 Routing Key로 발행하면 Exchange와 Binding이 실제 Queue를 결정한다. 처리 실패 시 requeue=false이면 DLX를 통해 DLQ로 이동한다.

      핵심 메모

      Direct는 정확히 일치하는 키, Topic은 패턴, Fanout은 전체 브로드캐스트다. RabbitMQ의 DLQ 이동은 consumer의 nack/reject와 requeue=false 결정에 직접 영향을 받는다.

      • Direct는 routing key와 binding key가 정확히 같을 때 전달한다.
      • Topic은 * 한 단어, # 여러 단어 패턴으로 전달한다.
      • Fanout은 routing key를 보지 않고 연결된 모든 Queue로 전달한다.
      • DLX는 실패 메시지를 DLQ로 보내는 Exchange다.

        Spring / Concurrency

        synchronized에서 Redis 분산락까지

        스터디룸 입장처럼 정원이 있는 기능은 동시에 들어오는 요청을 조심해야 한다. 처음에는 synchronized가 떠오르지만, Spring 서버가 여러 대가 되는 순간 락이 어디에 존재하는지부터 다시 봐야 한다.

        문제 상황

        예를 들어 정원이 3명인 스터디룸에 이미 2명이 들어와 있다고 하자. 거의 같은 순간에 두 명이 더 참가 요청을 보내면 둘 다 “아직 1자리 남았네?”라고 판단할 수 있다. 그러면 정원 3명짜리 방에 4명이 들어가는 일이 생긴다.

        이때 필요한 것이 동시성 제어다. 다만 락이라고 다 같은 락은 아니다. synchronized와 ReentrantLock은 Java 애플리케이션 내부의 락이고, Redis 분산락은 여러 서버가 같이 보는 외부 락이다.

        synchronized

        synchronized는 Java 객체가 가진 monitor lock을 이용한다. Spring Boot 서버 한 대 안에서 여러 스레드가 같은 메서드나 같은 객체의 임계 영역에 들어오려 할 때, 한 번에 하나의 스레드만 통과하게 만들 수 있다. 

        @Transactional
public synchronized void joinStudyroom(long studyroomId, long memberId) {
    Studyroom studyroom = studyroomRepository.findById(studyroomId)
            .orElseThrow();
    validateHeadCount(studyroom);
    memberStudyroomRepository.save(new MemberStudyroom(memberId, studyroomId));
}

        단순하고 읽기 쉽다. 하지만 이 락은 JVM 안에 있다. 서버 A의 synchronized와 서버 B의 synchronized는 서로를 모른다. 로드밸런서 뒤에 Spring 서버가 두 대라면, 각 서버는 자기 문만 잠그고 있는 셈이다.

          ReentrantLock

          ReentrantLock도 로컬 락이다. synchronized처럼 JVM 안에서 동작한다. 대신 lock, unlock을 직접 다루고, tryLock으로 기다리는 시간을 정하거나, studyroomId별로 락 객체를 관리하는 식의 제어가 가능하다. 

          private final ConcurrentHashMap<Long, ReentrantLock> locks = new ConcurrentHashMap<>();

public void joinStudyroom(long studyroomId, long memberId) {
    ReentrantLock lock = locks.computeIfAbsent(studyroomId, id -> new ReentrantLock());
    if (!lock.tryLock(2, TimeUnit.SECONDS)) {
        throw new StudyroomException(LOCK_TIMEOUT);
    }
    try {
        validateAndJoin(studyroomId, memberId);
    } finally {
        lock.unlock();
    }
}

          synchronized가 “이 메서드 문 하나 잠금”에 가깝다면, ReentrantLock은 “락 객체를 내가 골라서 관리”하는 느낌이 강하다. 예를 들어 studyroom:1과 studyroom:2는 서로 다른 락을 쓰게 만들어, 다른 방 입장까지 전부 막지 않게 만들 수 있다. 그래도 여전히 서버 한 대 안에서만 통한다는 한계는 그대로다.

            Redis 분산락

            서버가 여러 대라면 락도 여러 서버가 같이 볼 수 있는 곳에 있어야 한다. Redisson의 RLock을 쓰면 Spring Boot A와 Spring Boot B가 모두 Redis의 같은 키, 예를 들면 studyroomLock:1을 보고 입장 순서를 맞출 수 있다. 

            public void joinStudyroom(long studyroomId, long memberId) {
    RLock lock = redissonClient.getLock("studyroomLock:" + studyroomId);
    lock.lock();
    try {
        validateAndJoin(studyroomId, memberId);
    } finally {
        lock.unlock();
    }
}

            이제 락은 각 JVM의 기억 속이 아니라 Redis에 있다. 서버 A가 락을 잡으면 서버 B는 같은 키에서 기다린다. 그래서 분산 환경에서도 “같은 스터디룸에 대한 입장 검증”을 하나씩 통과시킬 수 있다.

              정리

              synchronized는 간단한 JVM 내부 직렬화에 좋다. ReentrantLock은 timeout, tryLock, 자원별 락 관리가 필요할 때 더 섬세하게 다룰 수 있다. 하지만 둘 다 로컬 락이다. 서버가 여러 대라면 같은 Redis lock key처럼 모두가 공유하는 기준이 필요하다.
